# The schema contract

Conductor publishes a machine-readable description of every MCP tool it
exposes — `dist/conductor-schema.json`, generated by `npm run build:schema`.
This doc is the contract that file represents: what's in it, what clients
can rely on, and what may change.

It exists because Conductor has more than one client. Claude Code discovers
tools at runtime over MCP and needs nothing else. A programmatic client —
[chess-board](https://github.com/chessser/chess-board), the TUI — needs to
validate inputs, generate typed calls, and render forms *before* a tool call
is made, which means it needs the tool definitions ahead of time, as data.

## Generated, never hand-written

`src/types/mcp-schema.ts` declares the tool list (`MCP_TOOLS`) and the
TypeScript input/output types. `src/lib/schema-generator.ts` turns that into
JSON Schema. Do not edit `dist/conductor-schema.json` — it's build output,
and the next build overwrites it.

`src/lib/schema-generator.test.ts` enforces the coupling: every tool in
`MCP_TOOLS` must have a generated schema, and the status enums must match
the `TaskStatus` union exactly. A type change that doesn't reach the schema
fails the test rather than silently shipping a drifted contract.

## Consuming it

```bash
npm install conductor
```

```typescript
import schema from 'conductor/schema';
import type { JiraSearchInput, ConductorTask } from 'conductor/types';
```

Both are declared in `package.json`'s `exports`. The schema is data (usable
from any language); the types are TypeScript-only convenience for Node
clients.

Four things a client can do with it:

1. **Validate inputs before calling** — `schema.tools['jira_search'].inputSchema`
   is JSON Schema, so any validator (ajv, etc.) can check a payload without
   a round-trip to the server.
2. **Generate typed clients** — tool names, input shapes, and output shapes
   are all present.
3. **Render forms** — required vs. optional fields, enums, and per-field
   descriptions are enough to build a create-issue form without hardcoding
   the fields.
4. **Type results** — e.g. `jira_search` returns `ConductorTask[]`.

## The guardrails are in the schema, structurally

`metadata.guardrails` names them, but the tool list itself is the real
statement, and the tests assert each one:

- **No delete tool exists** — no tool name matches `/delete|remove|destroy/`.
  This is [human-in-the-loop.md](human-in-the-loop.md)'s gate 2, visible to
  every client before a single call is made.
- **Every write is propose-then-confirm** — each backend has
  `*_propose_*` tools that return a token and a preview, plus exactly one
  `*_confirm_write` that takes only that token. There is no single-call
  write in the schema, so a client cannot construct one.
- **Reads and writes are project-scoped** — `jira_search`/`github_search`
  require a `projectKey`, which the server checks against what teams have
  declared in `kg-source` (see [mcp-server.md](mcp-server.md#guardrails)).

A client reading the schema cannot discover a way around any of these,
because the tools that would be needed to do so aren't there.

**The schema is a description, not the enforcement.** `src/mcp/write-guard.ts`
enforces scoping, token expiry, and single use on the server. A client that
ignores the schema gains nothing.

## Versioning

`schema.version` is semver, and it tracks the *contract*, not the codebase:

- **Patch** — descriptions, docs, internal changes with no wire effect.
- **Minor** — new tools, new optional input fields, new output fields.
  Additive; existing clients keep working.
- **Major** — removing a tool, renaming or newly-requiring an input,
  changing an output's shape or an enum's members.

Deprecations are announced a minimum of two minor versions before removal.
Every change is recorded in [SCHEMA_CHANGELOG.md](../SCHEMA_CHANGELOG.md),
which is separate from the code changelog on purpose — a client author cares
about wire-format changes, not refactors.

Clients should pin the `conductor` dependency and treat a major bump as
work, not an automatic upgrade.

## Backends

`metadata.backends` lists which issue trackers this build supports. Tools
are named per backend (`jira_*`, `github_*`) rather than taking a backend
parameter, so a client can tell from the tool list alone what's available.

Whether a given project actually resolves depends on the local
`.conductor/kg-source/` — the schema says a tool *exists*, not that any
particular project is reachable through it. A `github_*` call against a
project no team has declared is refused at runtime, exactly like the Jira
equivalent.
